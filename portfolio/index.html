Operational software · Browser demo + self-hosted app

GrizzWorks shop operations

  • JavaScript
  • Node.js
  • Server-Sent Events
  • Docker

The workflow: The crew moves work through a board and sees status on a wall display. The office follows jobs through quotes, inventory, and invoices without treating each step as a separate tracker.

The design: The browser demo and locally hosted app share business rules. The demo uses fictional records; the server handles shared state and pushes changes to connected screens. Posting updates receivables, the journal, and linked inventory. Corrections append reversing entries rather than silently editing posted history.

Customer implementation · Verified lab rehearsal

GrizzWorks data migration

  • Python
  • CSV validation
  • GrizzWorks REST API
  • Reconciliation

The cutover decision: I built a dry-run importer that blocks ambiguous dates, unresolved customer or job mappings, and duplicate IDs. Apply requires approval of the exact inputs and writes a new backup rather than editing the original.

What I verified: In a disposable GrizzWorks server, the corrected fixture imported four work orders totaling 7.50 estimated hours, preserved the original row, and survived a server restart. A replay proposed zero new orders. This was synthetic data, not a customer migration.

Release verification · Runnable Python sample

Edge Deployment Readiness Kit

  • Python
  • SHA-256
  • HTTP smoke test
  • JSON report

The handoff decision: A field site can’t download a replacement package on demand. I built a CLI that checks the target architecture and verifies every staged file against an approved release manifest before an operator proceeds.

What you can verify: Both sample files are present in the broken release, but one is the wrong revision. The CLI blocks it and tells the operator to restage the file. The corrected fixture passes staging; a separate optional HTTP check never implies that a cluster was deployed. The published reports use synthetic files, not a live K3s run.

Training and handoff · Live simulation

Grizzly Range

  • JavaScript
  • 5 training apps
  • 12 graded work orders
  • Local progress

The workflow: A learner opens a browser desktop, picks a work order, launches a training app, and checks their work against acceptance criteria. Exercises cover Git, command-line fundamentals, security awareness, and incident investigation using synthetic scenarios.

The design: A shared registry reads progress from each app’s existing browser save format. The work-order board stores its own completions without changing app saves when it validates them. The five apps still work on their own.
