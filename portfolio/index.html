01 / Operational software · public demo

GrizzWorks

  • JavaScript
  • Shared data model
  • Local storage
Try the sample shop ↗

What I built: A shop operations app that links work orders and inventory to jobs, quotes, and invoices. The crew gets a work board and the office can track the same job through billing.

Tradeoff: Drafts are editable, but corrections to posted invoices create reversing entries instead of overwriting the record. The public demo is easy to try because it stores fictional data in your browser, not in a shared deployment.

Verify it: Move a work order or open the wall display. For the accounting side, inspect the posting and reversal logic.

02 / Infrastructure · hands-on lab

Local infrastructure lab

  • Proxmox VE
  • Ubuntu Server
  • Docker
  • Tailscale
Inspect the lab hardware ↗

What I built: A self-hosted test environment on a Dell PowerEdge: Proxmox for virtualization, Ubuntu guests running Docker services, and Tailscale for private remote access.

Tradeoff: Running locally gives me control over the host and deployment environment, but it also makes patching, access, and recovery my responsibility.

Inspect it: Explore the hardware and service stack, then compare it with the worked rollout example for what I'd verify before an operator depends on a deployment.

03 / Product delivery · live app

AFT Forge

  • TypeScript
  • React
  • Offline PWA
  • GitHub Actions
Open AFT Forge ↗

What I built: An installable fitness planner that works offline and stores profiles and training logs on the phone, without an account.

Tradeoff: Local storage simplifies setup, but there's no cloud copy. Users can export a backup before clearing browser data or changing devices.

Verify it: Try the first-run flow. Read the GitHub Actions workflow to see how it checks for the manifest, service worker, and icons before publishing the app.
